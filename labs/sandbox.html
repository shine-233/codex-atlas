▮03 权限沙箱

同一个动作，换个模式就换一个判决。

MCP 工具不在保护范围内

      

        

          沙箱声明（02 的第 3 层）只描述内置 shell 工具的运行环境。
          经 MCP 服务器接入的工具完全绕开这套 Seatbelt / Landlock / WFP 信封——
          官方博客原话：它们「需自行负责执行其防护措施」。
        

        

          给模型接一个 MCP 文件服务器，它的删除操作不会因为 Codex 处于 read-only 而被拦截。
          能拦住它的只有两样：MCP 服务器自己的权限设计，和你会不会点那个「拒绝」。
        

      

    


    

      
另一条轴：审批策略

      
模式管「能不能」，审批管「要不要先问」。两者正交，CLI 上独立配置——上方判定器已接入这条轴，切换策略看琥珀格怎么变色。

      

        
策略行为

        
          
untrusted最保守：除少数白名单命令外都要人工批准。

          
on-failure沙箱内先跑；失败或被拦时请求升级重试。full-auto 预设 = workspace-write + on-failure。

          
on-request模型自行判断何时申请提权。

          
never从不打扰：拿不到的就直接失败，绝不弹窗。无人值守跑批常用。

        
      

      

        判定器里 workspace-write 对「写工作区外路径」给出的琥珀色结果，走的就是这条轴：沙箱说不行，但你可以点头放行一次。

证据边界

      三种模式与读取范围出自官方博客《Unrolling the Codex agent loop》及 openai/codex 公开文档；可写范围的具体规则出自固定提交下 codex-rs/protocol/src/permissions.rs 的 workspace_write()：工作目录 + /tmp + $TMPDIR 默认可写（各有 exclude 开关）、network_access 默认关闭。旧社区分析引用的 SandboxPermission/DiskWriteTempOnly 等枚举名在本基线已不存在——protocol 已拆成独立 crate，符号名以固定提交为准。强制执行机制按平台对应仓库目录：sandboxing/（Seatbelt）、linux-sandbox/ 与 bwrap/（Landlock/seccomp）。Windows 一列需特别说明：社区研究曾引用 windows-sandbox-rs/ 目录名；经查固定提交 @343074d4，workspace 成员名单中并无此 crate，但 workspace.dependencies 里仍保留指向它的路径引用（codex-windows-sandbox）——换一个提交就得重新查证，这是本站锁定基线的原因。
      审批策略对判定的影响是简化模型：never 把「条件放行」压成拒绝，untrusted 把白名单外的动作升级为先问；实际 CLI 中策略与沙箱模式的组合路径更细，具体开关名以固定提交下的 docs/config.md 为准。CONFIG BRIDGE 生成的键名（approval_policy、sandbox_mode、[sandbox_workspace_write] network_access)与「CLI 旗标覆盖配置文件」的优先级同出该文档；片段为形状示意。本页不运行真实命令，所有判定均为教学演示。
